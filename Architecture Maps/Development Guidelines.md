# Development Guidelines

How work is carried out on this project (process, not code style — for code style
see [Coding Conventions](./Coding%20Conventions.md)).

## Dev servers and ports

- **Do not start long-running dev servers** (`npm run dev`, `vite`, etc.). The
  author runs their own; a second one causes port/state conflicts and disrupts
  their workflow.
- **Never kill ports or processes** (`taskkill`, `pkill`, killing PIDs bound to a
  port). Other things are running on the machine.
- The client's Vite dev server is pinned to **port 1420** (Tauri convention) with
  `strictPort: true`, kept clear of Vite's default 5173. `tauri.conf.json`'s
  `devUrl` matches. Don't change this without a reason.

## Verifying changes

- **Verify headlessly.** Prefer `npm run build`, type/lint checks, unit tests, or
  one-shot scripts over booting a server and probing it.
- If a runtime or browser check is genuinely required, ask the author to run it —
  don't spin up a server to do it.
- **A passing build doesn't mean it works.** The "chapter text never saves" bug built
  cleanly for weeks. Anything that touches what the user does (typing, saving, clicking
  through a view) gets an end-to-end test that reproduces the action and reads the
  files the app wrote.

## End-to-end tests

`Main/Client/scripts/e2e-harness.mjs` runs the **real frontend** with no server and no
Tauri window:

- It builds the app with `vite build` into a temp folder and loads it from `file://` in
  headless Chrome (or Edge).
- Tauri's IPC is replaced by an **in-memory disk** seeded from
  `test project/Strongest World.project`. Dialogs, window close, and the Pandoc sidecar are
  stand-ins too (Pandoc writes a placeholder file; `E2E.pandocFail` makes it fail).
- Headless `--dump-dom` Chrome runs no rendering loop, so the harness ticks
  `requestAnimationFrame` on a 16 ms timer. App animations are frame-driven for this reason
  (Web Animations never finish there).
- A test is a driver script that runs in the page, clicks through the app, and calls
  `check(ok, label)`. Helpers include `openProject()`, `typeInto(cm, text)`, `file(path)`,
  `filesUnder(dir)`, `byText(selector, text)`, `setInput()` and `finish()`, which fails on
  any console error or failed disk call.
- Run one with `node scripts/e2e-<name>-test.mjs`. The suites are save, binder, scraps,
  export, outline and reveal (animation order, sampled frame by frame). Pass `screenshot` to `runE2E` to also save a PNG of the page.
- Pure logic has plain Node tests (`node scripts/<name>-test.mjs`). `export-test` also runs
  the bundled Pandoc for real on what the export builders produce.
- The fixture is generated by `node scripts/seed-project.mjs "<path>"` from the author's
  story board, which it only reads. Regenerating it changes every id, so tests must find
  things by name or structure, never by id or file name.

## Application principles

- **Self-contained / offline-first.** The app must fully work with **no internet
  connection**. All core features — writing, the project format, export — run locally
  with no external services or network calls. The *only* permitted network use is
  **checking for updates** (and downloading an update the user opts into). This means
  export tooling must be bundled (e.g. a Pandoc sidecar or in-app libraries), never a
  cloud API; fonts/assets ship with the app. "Downloadable marking packs" should also
  degrade gracefully offline (bundle a default set).
